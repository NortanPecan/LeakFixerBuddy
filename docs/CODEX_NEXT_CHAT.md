## Рекомендуемая модель и reasoning effort

Этот блок нужен не для максимального качества любой ценой, а для нормальной экономии ресурса чата и токенов.

Общее правило:

- если задача простая или локальная, не брать тяжёлую модель и высокий reasoning;
- высокий reasoning включать только там, где реально есть риск дорогой ошибки;
- новый чат открывать после завершения крупного этапа, а не тащить один переполненный диалог слишком долго.

### Базовая рекомендация по умолчанию

- Модель: `gpt-5.4-mini` или самый близкий лёгкий coding-вариант, если есть выбор
- Reasoning effort: `low` или `medium`

Это хороший режим для:

- чтения 1-3 файлов;
- локальных UI-правок;
- небольших API-фиксов;
- обновления handoff-файла;
- проверки конкретного бага в одном месте.

### Когда брать более сильную модель

- Модель: `gpt-5.4`
- Reasoning effort: `medium`

Использовать для:

- архитектурных решений;
- security-фиксов;
- сложных refactor-задач в нескольких связанных файлах;
- случаев, где легко пропустить регрессию.

### Когда повышать reasoning

- `high` — только если задача реально запутанная:
  - auth/security redesign;
  - сложная Prisma/SQL-логика;
  - race conditions;
  - большие shared refactor-изменения;
  - аудит, где нужно свести много разрозненных частей проекта.

- `xhigh` — почти никогда не нужен для этого проекта. Включать только если:
  - есть критичный production-инцидент;
  - нужно разрулить очень сложную цепочку зависимостей;
  - несколько прошлых попыток уже дали плохой результат.

### Практическая матрица для LeakFixerBuddy

| Тип чата | Модель | Reasoning |
|----------|--------|-----------|
| Быстро прочитать контекст и продолжить с handoff | `gpt-5.4-mini` | `low` |
| Небольшой UI/Telegram/API фикс в 1-3 файлах | `gpt-5.4-mini` | `low` или `medium` |
| Обычная рабочая сессия с правками в нескольких файлах | `gpt-5.4` | `medium` |
| Security-сессия, auth, owner-check, Telegram verification | `gpt-5.4` | `medium` или `high` |
| Большой аудит всего проекта | `gpt-5.4` | `high` |
| Мелкое обновление документации / handoff | `gpt-5.4-mini` | `low` |

### Как экономить токены на практике

1. Новый чат начинать с двух файлов:
   `CLAUDE.md` + `docs/CODEX_NEXT_CHAT.md`

2. Не просить модель “прочитать весь проект”, если задача локальная.

3. Для маленьких задач явно писать область:
   например: `проверь только src/app/api/auth/route.ts и src/lib/auth-telegram.ts`

4. После завершения крупного этапа обновлять handoff и переходить в новый чат, вместо того чтобы тащить длинный диалог дальше.

5. Для простых действий выбирать `low`, а не держать `high` по умолчанию.

## Самый важный технический вывод

Критическая проблема безопасности подтверждена: backend в основном доверяет `userId`, который приходит с клиента.

Это значит:

- проблема не только в отсутствии owner-check в API;
- корневая проблема глубже: сейчас нет нормальной серверно-проверяемой сессии, на которую можно опереться;
- поэтому нельзя начинать с массового прохода по `~90` API-роутам и просто добавлять `getAuthenticatedUser(request)`, если этот helper по-прежнему будет читать клиентский `userId`.

Иными словами: сначала нужно укрепить серверную аутентификацию, потом уже раскатывать auth guard по API.

## Что уже подтверждено по коду

### 1. `src/lib/auth.ts`

Не валидирует владельца данных. Читает `userId` из header/query/body.

### 2. `src/app/api/auth/route.ts`

- есть обход через `GET /api/auth?owner=true`;
- есть demo-вход через `GET /api/auth?demo=true`;
- Telegram auth в этом роуте умеет проверять HMAC только если настроен `TELEGRAM_BOT_TOKEN`;
- при отсутствии токена роут доверяет данным клиента и разбирает `user` без нормальной проверки подписи.

### 3. `src/app/api/auth/telegram/route.ts`

Использует `src/lib/auth-telegram.ts`, где HMAC-проверка фактически не реализована.

### 4. `src/app/api/auth/email/route.ts`

Пароли хешируются через SHA-256 с солью. Это слишком слабая схема для production. Нужен `bcrypt` или `argon2`.

### 5. Самые опасные API-роуты

В первую очередь закрывать:

- `src/app/api/user/route.ts`
- `src/app/api/settings/route.ts`
- `src/app/api/challenges/route.ts`
- `src/app/api/buddies/route.ts`
- AI-роуты, которые тратят квоту и работают от имени пользователя

## Когда переходить в новый чат

Открывать новый чат имеет смысл в одном из этих случаев:

1. Завершён отдельный этап работы.
   Пример: закрыли `owner/demo`, закончили Telegram HMAC, закончили rollout guard на критичные API.

2. Контекст разросся настолько, что перед каждым новым шагом приходится заново объяснять много деталей.
   Практический признак: чтобы продолжить, нужно пересказывать больше 5-7 файлов или длинную цепочку решений.

3. Предстоит большой новый блок работ с другой фокусной областью.
   Пример: после security перейти отдельно к rate limiting, затем отдельно к архитектурной чистке HomeScreen.

4. Чат стал “тяжёлым” и хуже держит рабочую нить.

## Как эффективно работать с Codex

### Базовый принцип

Один чат = один понятный рабочий этап.

Хорошие примеры одного этапа:

- закрыть `owner/demo` обходы;
- починить Telegram HMAC;
- раскатить auth guard на критичные API;
- сделать конкретную UI-фичу в 1-2 экранах.

Плохой вариант:

- смешивать в одном чате security, Telegram UX, HomeScreen perf, migrations и product brainstorm.

### Когда лучше оставаться в текущем чате

- задача всё ещё в том же этапе;
- я помню контекст без длинного пересказа;
- мы работаем в одном и том же наборе файлов;
- чат не стал тяжёлым и ответы не начали расползаться.

### Когда лучше открыть новый чат

- закончили отдельный этап;
- переключаемся на новую подсистему;
- приходится снова и снова пересказывать старые решения;
- в чате уже слишком много контекста и он мешает скорости;
- хочется сменить модель/reasoning под другой тип задачи.

### Что буду делать я

Да, я могу сам подсказывать, когда пора сменить чат.

Обычно я буду говорить об этом в одном из таких случаев:

- этап завершён и лучше зафиксировать handoff;
- дальше начинается отдельный большой блок работ;
- текущий чат уже перегружен контекстом;
- безопаснее перейти в новый чат, чтобы не тащить за собой лишние допущения.

### Практичный режим для новичка

Если только привыкаешь к Codex, самый удобный режим такой:

1. Один чат на одну задачу или один этап
2. В конце этапа попросить: `обнови docs/CODEX_NEXT_CHAT.md`
3. Новый чат начинать с:
   `Прочитай CLAUDE.md и docs/CODEX_NEXT_CHAT.md, продолжай`
4. Для мелочей брать лёгкую модель и низкий reasoning
5. Для security и архитектуры брать более сильную модель и не смешивать это с мелкими правками

Этот режим обычно даёт лучший баланс между качеством, скоростью и расходом контекста.
