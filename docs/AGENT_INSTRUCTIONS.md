# Инструкции для агента

## Правила работы агента (обязательно читать перед работой)

Этот раздел описывает, КАК агент должен работать с проектом LeakFixer.  
Любая сессия работы с кодом должна следовать этим правилам.

---

### 1. Вход в сессию

Перед началом работы агент обязан:

1. **Проверить текущую ветку и при необходимости переключиться:**
   - Выполнить `git branch` — убедиться, что активна ветка `main`.
   - **Если активна ветка `master` — это ОШИБКА!** Нужно переключиться на `main`.
   - **Рабочая ветка проекта: `main`** — ВСЕГДА работать только в ней.
   - Ветка `master` — историческая, НЕ используется, НЕ переключаться на неё.
   - Если локально нет ветки `main`, выполнить: `git checkout main` (создаст её из `origin/main`).
2. Выполнить и ПРОЧИТАТЬ результаты (не изменяя состояние репозитория):
   - `git status` — чтобы понять, есть ли незакоммиченные изменения.
3. Перечитать:
   - `docs/CURRENT_STATE.md` — текущее состояние проекта;
   - `docs/AGENT_INSTRUCTIONS.md` — этот файл;
   - `worklog.md` — последние выполненные шаги.
4. В `worklog.md` добавить короткую строку:
   - `[#] Перезапуск сессии: что увидел по git status и текущему состоянию`.

Агент не имеет права делать выводы о состоянии проекта «по памяти» без чтения этих файлов.

---

### 2. Ограничения на действия

#### 2.0. База данных (КРИТИЧЕСКИ ВАЖНО)

**ПРОЕКТ ИСПОЛЬЗУЕТ SUPABASE POSTGRESQL ЧЕРЕЗ REST API!**

Агенту ЗАПРЕЩЕНО:
- Создавать локальную SQLite базу данных
- Конвертировать схему Prisma под SQLite
- Менять `provider = "postgresql"` на `provider = "sqlite"` в schema.prisma
- Создавать файлы типа `dev.db`, `prisma/dev.db`
- Предлагать использовать локальную базу для разработки

База данных ВСЕГДА работает через Supabase:
- Использовать `src/lib/supabase-rest.ts` для REST API запросов
- Prisma схема использует `provider = "postgresql"`
- ENV переменные: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `DATABASE_URL`

**НЕ НАДО "УПРОЩАТЬ" ИЛИ "АДАПТИРОВАТЬ" ПОД ЛОКАЛЬНУЮ РАЗРАБОТКУ!**

#### 2.1. Git и ветки

**РАБОЧАЯ ВЕТКА: `main`** — ВСЕГДА работать только в ней!

Агенту ЗАПРЕЩЕНО:
- Переключаться на ветку `master`
- Предлагать слить `master` в `main` или наоборот
- Использовать `master` как рабочую ветку

Агенту ЗАПРЕЩЕНО самостоятельно выполнять любые git‑команды, включая:

- `git add`, `git commit`, `git push`;
- `git pull`, `git fetch`;
- `git merge`, `git rebase`;
- `git reset`, `git checkout`, `git switch`.

Агент может только:

- описывать, какие git‑команды пользователь ДОЛЖЕН выполнить;
- приводить план в виде списка шагов.

Реальные git‑команды всегда выполняет человек, не агент.

#### 2.2. Конфиги и деплой

Без явного прямого запроса ЗАПРЕЩЕНО:

- менять CI/CD конфигурации, Docker‑файлы, скрипты деплоя;
- менять ветку, в которую идёт деплой (например, `main`/`master`);
- переписывать `package.json` в части скриптов, версий и зависимостей.

Любые изменения в этих областях агент должен оформлять сначала как предложение в `worklog.md` и в ответе пользователю.

---

### 3. Правила при «зависании» и перезапуске

Если сессия была прервана (агент остановлен) и затем запущена снова:

1. Агент НЕ ДОПУСКАЕТ, что «помнит» предыдущее состояние.
2. Протокол перезапуска:
   - снова выполнить `git status` (только чтение, без изменений);
   - перечитать `worklog.md` (последние шаги и планы);
   - перечитать этот файл (`AGENT_INSTRUCTIONS.md`);
   - в `worklog.md` кратко описать:
     - что видит по git;
     - какой последний завершённый шаг;
     - какой следующий безопасный шаг он предлагает.
3. Агент НЕ ДОЛЖЕН:
   - пытаться «откатывать» файлы;
   - «восстанавливать» старые состояния;
   - автоматически синхронизировать версии кода с удалённым репозиторием.

Любые несоответствия версий (локально vs remote) агент только описывает и предлагает план действий человеку.

---

### 4. Формат работы над задачами

Каждая задача должна быть разбита на маленькие шаги.

Для каждого шага агент обязан:

1. В начале шага:
   - добавить запись в `worklog.md`:  
     `### [дата] Шаг N: <краткое описание> — СТАРТ`;  
   - описать план из 2–5 подпунктов (что будет делать).
2. В ходе работы:
   - изменять только те файлы, которые относятся к шагу;
   - не трогать структуру проекта и конфиги, если это не часть шага.
3. В конце шага:
   - описать результат в `worklog.md`:
     - какие файлы изменены;
     - что именно сделано;
     - какие проверки выполнены (lint, dev‑сервер и т.д.);
   - убедиться, что проект собирается и запускается (если это релевантно шагу).

Git‑команды в рамках шага агент не выполняет, только предлагает.

---

### 5. Обращение с «несовпадениями версий» и конфликтами

Если агент замечает:

- конфликт при merge/rebase;
- расхождение между локальной веткой и удалённой (`origin/main` и т.п.);
- ошибку, связанную с версиями файлов или зависимостей,

он обязан:

1. НЕ выполнять никаких автоматических git‑команд.
2. В `worklog.md` и в ответ пользователю:
   - привести текст ошибки/состояния (словами);
   - описать, что именно, по его мнению, произошло;
   - предложить план действий для пользователя в формате:
     1. «Сделай `команда1`»
     2. «Затем `команда2`»
3. Дождаться решения пользователя и не предпринимать самостоятельных действий по «восстановлению» или «сбросу».

---

### 6. Работа с окружениями: песочница и онлайн

В проекте есть минимум две среды:

- **Песочница (sandbox / локальная разработка)** — среда, в которой обычно работает пользователь локально.
- **Онлайн‑версия (prod)** — связана с боевым Supabase/деплоем.

Агент обязан:

1. Явно понимать, в какой среде он работает:
   - в начале сессии прочитать `docs/CURRENT_STATE.md` и раздел про окружения;
   - не делать предположений «по умолчанию» о том, какая БД используется.
2. Все решения по окружениям оформлять через env‑переменные, а не через жёстко прописанные URL/ключи в коде.
3. Никогда не смешивать настройки песочницы и онлайн‑версии в одном конфиге:
   - если добавляются новые env, чётко описать их назначение в `CURRENT_STATE.md` и в этом файле;
   - не переиспользовать переменные prod‑окружения для sandbox и наоборот.

Если агенту нужно изменить логику выбора окружения, он:

- сначала описывает предлагаемую схему (какие env, какой файл и как выбирает среду) в `worklog.md`;
- затем вносит изменения в код;
- не трогает реальные значения env, .env‑файлы с секретами остаются под контролем пользователя.

---

### 7. Общее правило безопасности

Если агент сомневается, можно ли делать действие автоматически, он должен считать, что **нельзя**, и:

- описать ситуацию в `worklog.md`;
- задать уточняющий вопрос пользователю;
- предложить план, но не выполнять его сам.
